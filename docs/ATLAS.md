# Feature atlas

The atlas is a set of JSON records, one per gameplay system found in a module
("feature"), plus a generated inventory. The JSON is the source of truth.

## Folder layout

Under `ATLAS_DIR` (env `WB_ATLAS_DIR`, default `<repo>/out/atlas`):

    features/<slug>.json     one file per investigated module: {"module": "<slug>", "features": [ ... ]}
    overlaps.json            {"_doc": "...", "mechanics": {"<mechanic name>": ["<feature id>", ...]}}
    FEATURE_INVENTORY.md     generated by `inventory` (do not edit)
    auto/<slug>.md           generated by `report <slug>` (a mechanical starting map, not a verdict)

A missing `ATLAS_DIR` or `features/` folder means zero records, not an error.

## Commands

    features [REGEX] [--cat C] [--module M]   search records
    feature ID                                show one record in full
    features-check                            validate every record against atlas_schema.json
    overlaps-apply                            copy overlaps.json into each record's `overlaps`
    inventory                                 regenerate FEATURE_INVENTORY.md
    report MOD|all                            write auto/<slug>.md

`features-check` reports a record with a missing `category` once ("missing category"); it does not
also report a bad category for it. `overlaps-apply` rewrites each feature file with `indent=2`
(and a trailing newline), so the first run on hand-formatted files can change their layout.

## Record fields

Facts about the module are required; judgements against a target module are optional.
All keys in the "required" group must be present (use `[]` or `""` when not applicable).

Required (facts):
- `id` - `"<slug>.<short_snake_name>"`, unique and stable.
- `name` - human name, e.g. "Lord patrols around fiefs".
- `category` - one of the categories below.
- `summary` - 1-3 sentences: what the player experiences / what it does.
- `mechanics` - how it works, plainly (triggers -> scripts -> state -> effect).
- `hooks` - entry-point block ids (`strig:N`, `mst:x/tK:conseq`, `menu:...`, `dlg:...`, `script:game_*`).
- `scripts` - script names that make up the system.
- `slots` - `["party:44", "troop:150", ...]` (object:slot).
- `globals` - global names.
- `native_relation` - enum, see below.
- `confidence` - enum.
- `evidence` - list of short evidence strings (commands run, block ids, findings).

Optional (judgement, only meaningful when you compare against a target module; each is
enum-checked when present, and `features-check` passes without them):
- `target_status` - enum: does the target (main) module already have this?
- `target_evidence` - what in the target is similar (block ids / scripts) or why it is absent.
- `conflicts` - concrete conflicts with the target module (script, slot, global, trigger, menu).
- `difficulty`, `risk`, `recommendation` - enums.
- `value` - integer 1-5, gameplay value for the target module.

Optional (content):
- `menus`, `presentations`, `mission_templates`, `dialogs` - ids.
- `resources` - `{"pt": [...], "troop": [...], "item": [...], "scene": [...], ...}` module-specific content.
- `overlaps` - feature ids in other modules implementing the same mechanic (filled by `overlaps-apply`).
- `notes` - free text.

The inventory shows a dash for a judgement a record lacks, and leaves a judgement column out
entirely when no record has it. A worked example with facts only is in `examples/atlas/`.

## Enums

- `native_relation`: `new`, `modifies-native`, `replaces-native`, `native-identical`
- `target_status`: `absent`, `partial`, `present`, `different-implementation`
- `difficulty`: `low`, `medium`, `high`, `very-high`
- `risk`: `low`, `medium`, `high`
- `recommendation`: `adopt`, `adapt`, `reference`, `skip`
- `confidence`: `confirmed`, `strongly-inferred`, `speculative`

The target module is the registry entry with role `main`. The inventory labels
the comparison column with that module's label, or "target" when there is none.

## Confidence rule

`confirmed` needs at least 2 independent evidence kinds (for example a
disassembly of the entry point plus a caller/slot/global trace, or a
disassembly plus displayed text). One kind of evidence is `strongly-inferred`
at best; a guess from names alone is `speculative`.
